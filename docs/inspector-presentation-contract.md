# Inspector presentation contract

Status: **Accepted reference for new Inspector work**. The hardened Touchpoint Inspector is the reference implementation, not a claim that Product and Offer already comply or that the proposed architecture is final.

Read this contract and the [Inspector interaction contract](./inspector-interaction-contract.md) during Plan/task-stub preparation, before proposing Inspector work. `AGENTS.md` and `PRODUCT.md` define governance, product boundaries, and ontology; accepted decisions follow; runtime code defines actual behavior; tests provide regression evidence; these contracts must be corrected when they diverge. Old implementation notes and screenshots are diagnostic clues only. A missing test or incidental CSS value does not become a contract.

## Document frame and reading order

- `MapSpike.tsx` and `.inspector`/`.inspector-header` own the document frame. Keep header identity first, then semantic sections in this reference order: Business structure, derived Neighborhood, Client Scope, Resistance. Omit inapplicable sections rather than manufacture symmetry.
- The header separates the `.inspector-title-button` editing surface from type/side metadata, `.inspector-business-lineage` entity links, and `.inspector-history`. Business lineage is a Touchpoint projection of complete Product → Offer → Touchpoint ancestry, not generic breadcrumbs.
- Back/Forward are document navigation. Entity links use the shared text-like underlined accent treatment; authoring actions, `.inspector-secondary-action`/dismissal, status metadata such as `Derived`, and transient disclosure controls must remain visually distinguishable.
- `.inspector` uses adaptive padding; the header/form use the available document width and the current `72rem` maximum. This available-width principle is consequential. The exact padding expression and maximum are current shared implementation values, not permission to clone constants into a new Inspector.

## Business structure

`touchpointBusinessStructureSection` consumes `deriveTouchpointBusinessStructure()`. `.business-structure-regions` currently uses a primary/containment two-column grid (`minmax(0, 1.6fr) minmax(12rem, 1fr)`, gaps `1rem 1.5rem`) and collapses at `max-width: 42rem`. The distinct regions, readable source order, `min-width: 0`, and narrow collapse are contractual; those exact values are current shared-owner values and must be changed centrally rather than copied.

- Structural property headings use `.inspector-property-heading-action` and the single `Click to edit` hint. The heading opens the local editor; a rendered entity value navigates. Never merge both meanings into one primary target.
- Placement contains Offers, Located in and URL. Containment contains Parent and Children. These labels and semantics are Touchpoint-specific.
- Offers/Parent/Children render entity links in read state. Located in renders a registry reference, not fake entity navigation. A safe URL is one external link; empty or unsafe URL remains readable/editable without external-link semantics.
- Empty authored properties use the shared edit-value/empty treatment. Invalid inputs retain the editor and show its error; unavailable candidates/data use explicit text or disabled state, never a misleading live link.
- `.business-structure-property`, `.business-structure-links`, `.business-structure-edit-value`, shared heading actions, and embedded editor classes are the reusable example. Do not reproduce entity-specific JSX/CSS just to rename a property.

## Embedded relation editors

- `.inspector-relation-editor` remains local where the property value was displayed. Candidate rows compose a native input, `.inspector-relation-indicator`, and wrapping label text. Checkbox-like rows support multi-select; radio-like rows support single-select.
- Search is progressively disclosed when the candidate space reaches the current `RELATION_EDITOR_SEARCH_THRESHOLD` (`7`). The appearance of search is portable; the number is current implementation, not an immutable cross-ontology threshold. Filtering and eligibility remain owner-defined.
- Optional Clear is an explicit action, not a synthetic candidate. Explicit compact Close dismisses the editor. Nested Back changes editor level; destructive confirmation shows the exact impact with separate Cancel/Confirm affordances.
- A primary candidate row selects; it does not also navigate. Provide navigation outside local editing when it is meaningful.
- Current `1rem` checkbox and `.9rem` custom indicator values are implementation details, not proven universal accessible targets. Preserve the implemented full-row hit area, visible focus, wrapping and layout stability; verify actual pointer/keyboard target geometry in a browser.

## Derived Neighborhood

`NeighborhoodGroups` is the shared renderer used by Touchpoint and Offer. It owns the heading plus `Derived` status, compact ground-type overview and focus controls, cards, disclosure, count badges, link lists, empty state, expanded-first/collapsed-after ordering, and stable identity. Entity assemblers supply explicit ground-type metadata, ground/basis metadata, and neighbors; a neighbor is deduplicated within a ground but may correctly appear under multiple grounds. A presentation group may optionally supply read-only rich expanded content through the shared callback slot, which receives the existing `onNavigate`; without it, the renderer uses the unchanged shared neighbor-link list. The slot cannot own disclosure, focus/filter state, card identity, or layout.

- The compact overview contains one native checkbox for each type represented by the supplied nonempty grounds, deduplicated by `groundTypeId` in first-appearance order. Its named type and mode groups, labels, and Reset action wrap at narrow widths without clipping meaningful text or causing horizontal overflow. Controls retain a visible `:focus-visible` indication.
- With selected types, Dim preserves the complete ordered card set and packed panel-ID input while applying only a semantically neutral visual de-emphasis to nonmatching cards. Dimmed cards and their disclosure/entity links remain keyboard-operable and are not disabled, hidden from accessibility APIs, inert, or removed from tab order. An empty selection removes all de-emphasis regardless of mode.
- Hide renders and measures the same filtered ordered set of matching cards, passing only their IDs to the existing packed-layout owner so measurements and container height reflow without stale panels. Returning to Dim or resetting restores the full ordered set and its unchanged geometry/disclosure state. No alternate layout algorithm or entity-specific width/modifier is introduced.
- `initialCompactOverviewExpandedGroupIds()` supplies initial compact disclosure density: one group of at most four opens; two groups open when each is at most four and their total is at most six; otherwise groups start collapsed. This current common overview rule does not establish domain semantics.
- `usePackedPanelLayout` is the generalized measured-layout owner. Neighborhood uses current 14–20rem tracks and `.65rem` gap; the CSS Grid fallback is `repeat(auto-fit, minmax(min(100%, 14rem), 20rem))`, left aligned, and becomes one column under the current `30rem` media query. Adaptive use of available width and narrow fallback are contract; constants remain shared implementation values.
- Expanded groups precede collapsed groups visually and in the renderer's ordered list. Stable group IDs preserve disclosure state. Variable measured heights feed shortest-column placement; CSS Grid remains readable when `ResizeObserver` is unavailable.
- Rich content remains inside the existing disclosure content. Offer semantic cards use ordinary Inspector entity links for their concrete basis and neighboring Offers. DO-bearing Job cards may reuse the mini-dendrite vocabulary for Job → Desired Outcome comparison categories, while preserving the shared 14–20rem geometry, wrapping, packed-layout input, and focus grammar. This presentation capability does not make Offer ontology a shared renderer concern.
- The hook owns measured container height and absolute transforms. A future user reuses it rather than adding a packing algorithm. Browser checks must measure columns, variable heights, overlap, horizontal overflow and resize recalculation; pure `calculatePackedPanelLayout` tests cannot prove rendered geometry.

## Client Scope read state

The Touchpoint read projection comes from `touchpointClientScope()`. It renders nonempty panels for the six canonical kinds: Core Functional Job, Related Job, Consumption Chain Job, Emotional Job, Social Job, and Financial Desired Outcome.

- Panels use count badges and independent progressive disclosure. DO-bearing Jobs show Job → Desired Outcome mini-dendrites; Emotional/Social Jobs do not acquire fake ordinary outcomes; Financial Desired Outcome is an independent leaf. Titles are semantic entity navigation links.
- The same `initialCompactOverviewExpandedGroupIds()` density and expanded-first presentation apply. `ClientScopePackedGroups` calls `useClientScopePackedLayout` with current 18–22rem panels and `.65rem` gap. `.client-scope-view-groups` provides the readable auto-fit Grid fallback.
- Stable panel IDs, logical DOM/focus order, measured visual placement, explicit container height, and resize recalculation are contractual. Packed visual coordinates must not be mistaken for ontology or persisted order.
- Resistance remains outside the Client Scope panel grid because it is a different derived/authored semantic surface, not a seventh Client kind.

## Client Scope edit state and Resistance

- The edit state stays within the persistent Client Scope section. `Search Client intent`, compact kind shortcuts, and upstream-source disclosures expose global discovery and provenance. Candidate presentation must distinguish checked, incomplete, invalid and contributor-resolver states.
- `globalIntentDiscovery()` and `touchpointUpstreamSources()` own the projection; contributor choices and eligibility are not presentation inventions. A DO-bearing path remains visibly incomplete until its outcome/contributor context is resolved.
- `touchpointResistanceSection` presents relevant Repulsors with a `Derived` marker, navigable Repulsor title, and authored `Mitigated here` checkbox. Derived relevance must not resemble or silently become authored mitigation.

## Cross-cutting presentation

- Follow existing type hierarchy (document title, section heading, structural heading, property heading, metadata/status), spacing rhythm, border/color vocabulary, and shared control classes. Accent-underlined entity links communicate navigation; buttons communicate authoring/dismissal; muted chips/text communicate metadata, not actions.
- Consequential values currently include the document maximum, Business grid/collapse, compact panel min/max/gaps, narrow Neighborhood fallback, `min-width: 0`, wrapping, and measured container height. Change them only at their shared owners with regressions. Border radii, padding, font sizes, and indicator dimensions are current implementation unless evidence shows layout/accessibility significance.
- Long text wraps; flex/grid children keep `min-width: 0`; external URLs and link lists must not cause horizontal overflow. Visible `:focus-visible` styling is required wherever the current shared classes provide keyboard interaction.
- There is no accepted viewport matrix. CSS breakpoints currently in `styles.css` describe implementation, not promised device support. Test available container width, not viewport alone.
- Ontology can justify different fields, relations, eligibility, copy and derived grounds. It does not justify parallel widths, cards, disclosure models or action styling.

## Reuse boundary

**Reuse:** document frame; semantic visual language; heading edit affordance; entity-link treatment; local embedded editors; semantic-completeness commit presentation; dismissal/focus grammar; disclosure state model; adaptive/packed panels; navigation/history; validation and confirmation boundaries.

**Do not copy literally:** Product → Offer → Touchpoint structure; Offers, Located in, Parent or Children; Touchpoint containment/reassignment; six Client Scope kinds as mandatory sections; contributor propagation; Resistance relevance/mitigation; specific labels, counts or empty copy; Touchpoint candidate eligibility or domain operations.

A future Inspector first identifies its ontology-owned properties and relations, then applies the common presentation and interaction contracts.

## Maintenance and evidence rule

An accepted common-pattern change must update in one change: (1) this or the interaction contract, (2) the shared implementation owner, (3) regressions for the Touchpoint reference, and (4) regressions for every other affected Inspector kind. An entity-specific exception requires an ontology rationale. A small present card count never justifies a separate width or disclosure contract.

A screenshot is insufficient. Browser geometry (real container width, wrapping, focus visibility, differing measured heights, resize, overlap and overflow) must complement pure layout tests and DOM/accessibility semantics. Record unverified behavior explicitly as current implementation, browser-only observation, missing regression guard, unresolved product/ontology question, or legacy behavior scheduled for replacement.
