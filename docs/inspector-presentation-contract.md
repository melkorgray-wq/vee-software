# Inspector presentation contract

Status: **Accepted reference for new Inspector work**. The hardened Touchpoint Inspector remains the common reference implementation, and Offer Business structure is an accepted entity-specific adaptation of the shared presentation grammar. This does not claim that the proposed architecture is final or that the whole Offer Inspector complies: Offer Client intent retains legacy section-wide Apply debt.

Read this contract and the [Inspector interaction contract](./inspector-interaction-contract.md) during Plan/task-stub preparation, before proposing Inspector work. `AGENTS.md` and `PRODUCT.md` define governance, product boundaries, and ontology; accepted decisions follow; runtime code defines actual behavior; tests provide regression evidence; these contracts must be corrected when they diverge. Old implementation notes and screenshots are diagnostic clues only. A missing test or incidental CSS value does not become a contract.

## Document frame and reading order

- `MapSpike.tsx` and `.inspector`/`.inspector-header` own the document frame. Keep header identity first, then semantic sections in this reference order: Business structure, derived Neighborhood, Client Scope, Resistance. Omit inapplicable sections rather than manufacture symmetry.
- The header separates the `.inspector-title-button` editing surface from type/side metadata, `.inspector-business-lineage` entity links, and `.inspector-history`. Business lineage is a Touchpoint projection of complete Product → Offer → Touchpoint ancestry, not generic breadcrumbs.
- Back/Forward are document navigation. Entity links use the shared text-like underlined accent treatment; authoring actions, `.inspector-secondary-action`/dismissal, status metadata such as `Derived`, and transient disclosure controls must remain visually distinguishable.
- `.inspector` uses adaptive padding; the header/form use the available document width and the current `72rem` maximum. This available-width principle is consequential. The exact padding expression and maximum are current shared implementation values, not permission to clone constants into a new Inspector.

## Business structure

`touchpointBusinessStructureSection` consumes `deriveTouchpointBusinessStructure()`. `.business-structure-regions` currently uses a primary/containment two-column grid (`minmax(0, 1.6fr) minmax(12rem, 1fr)`, gaps `1rem 1.5rem`) and collapses at `max-width: 42rem`. The distinct regions, readable source order, `min-width: 0`, and narrow collapse are contractual; those exact values are current shared-owner values and must be changed centrally rather than copied.

- Structural property headings use `.inspector-property-heading-action` and the single `Click to edit` hint. The heading opens the local editor; a rendered entity value navigates. Never merge both meanings into one primary target.
- Placement contains Offers, Located in and URL. Containment contains Parent and Children. These labels and semantics are Touchpoint-specific.
- Offers/Parent/Children render entity links in read state. Located in renders a registry reference, not fake entity navigation. A safe URL is one external link; empty or unsafe URL remains readable/editable without external-link semantics.
- Empty authored properties use the shared edit-value/empty treatment. Invalid inputs retain the editor and show its error; unavailable candidates/data use explicit text or disabled state, never a misleading live link.
- `.business-structure-property`, `.business-structure-links`, `.business-structure-edit-value`, shared heading actions, and embedded editor classes are the reusable example. Do not reproduce entity-specific JSX/CSS just to rename a property.

### Offer-specific adaptation

Offer Business structure applies the same two-column presentation grammar through two entity-specific structural regions: **Product** and **Presentation**. This is an accepted adaptation, not a second layout system and not a claim that all Offer sections have left legacy editing behind.

- **Product** represents the one mandatory direct `product_packaged_as_offer` relation. Its committed title is a distinct entity-navigation action, while its heading uses the accepted `Click to edit` single-select relation-editor affordance. Because the relation is mandatory, the editor offers no `Clear` action.
- **Presentation** shows only directly committed Connected Touchpoints from `offer_presented_at_touchpoint`. An empty Connected Touchpoints list is valid because an Offer need not be related to a Touchpoint. Committed titles retain entity navigation in read view.
- The Connected Touchpoints heading uses `Click to edit`, and its embedded multi-select reuses the shared relation-editor grammar. A candidate row may show compact committed context: `Root` or `Child`, plus the number of directly linked Offers. `Root`/`Child` is derived from Touchpoint containment; the count is derived from direct valid `offer_presented_at_touchpoint` relations.
- Candidate metadata is row context, not a separate control, eligibility rule, or persisted Offer property. `Child` status alone never prohibits attach, detach, or replacement.

Offer Presentation is not containment, and Offer acquires no Parent/Children semantics. `Root`/`Child` describes the candidate Touchpoint in its own containment topology, never a position inside an Offer. The shared two-column grammar does not make Product/Presentation ontologically equivalent to Touchpoint Placement/Containment. Layout, responsive collapse, wrapping, and focus rules remain centralized shared owners; there is no Offer-specific width contract.

### Offer Content

Offer Content is an optional Offer-owned major section between Business structure and Neighborhood. It is separate from both. Its authored minimum is one optional external document `contentUrl` and one optional free-form `contentText`; the values are independent and may coexist. Absence of both is a valid compact neutral state (`No content documented`), not an invalid or incomplete Offer. The URL is an external navigation value of the Offer itself—not Evidence, a Touchpoint, a Connected Touchpoint, or a separate attachment/entity model. The `.offer-content` wrapper follows the shared Inspector content edge without generic `section` card chrome while retaining its local internal layout.

Read state specializes the shared [Document frame](#document-frame-and-reading-order), [Cross-cutting presentation](#cross-cutting-presentation), and reusable editor rules rather than restating their wrapping, focus-visible, external-link, or semantic-heading affordances:

- Multi-paragraph text initially renders its first nonempty paragraph; this is content-aware preview selection, not a CSS line clamp. **Show more / Show less** changes transient presentation state only.
- Expansion records the disclosure control's viewport offset and scroll owner. Collapse restores that prior offset when the same control, Offer, text, and scroll context remain eligible; it does not unconditionally scroll to the section start. Disclosure and its scroll snapshot are neither authored nor document state.
- **Copy** appears only when `contentText` exists and copies the complete value regardless of disclosure state. Disclosure and Copy are peer actions for one text object in a compact, local, left-aligned cluster; the same cluster remains valid when Copy is its only action.

URL/text meaning and ownership are Offer-specific. The confirmed transferable mechanisms are only the implemented local property editor, transient disclosure and contextual scroll restoration, compact peer-action grouping, and owner-aware focus/dismissal behavior.

## Embedded relation editors

- `.inspector-relation-editor` remains local where the property value was displayed. Candidate rows compose a native input, `.inspector-relation-indicator`, and wrapping label text. Checkbox-like rows support multi-select; radio-like rows support single-select.
- Search is progressively disclosed when the candidate space reaches the current `RELATION_EDITOR_SEARCH_THRESHOLD` (`7`). The appearance of search is portable; the number is current implementation, not an immutable cross-ontology threshold. Filtering and eligibility remain owner-defined.
- Optional Clear is an explicit action, not a synthetic candidate. Explicit compact Close dismisses the editor. Nested Back changes editor level; destructive confirmation shows the exact impact with separate Cancel/Confirm affordances.
- A primary candidate row selects; it does not also navigate. Provide navigation outside local editing when it is meaningful.
- Current `1rem` checkbox and `.9rem` custom indicator values are implementation details, not proven universal accessible targets. Preserve the implemented full-row hit area, visible focus, wrapping and layout stability; verify actual pointer/keyboard target geometry in a browser.

## Derived Neighborhood

`NeighborhoodGroups` is the shared renderer used by Touchpoint and Offer. It owns the heading plus `Derived` status, compact ground-type overview and focus controls, cards, disclosure, count badges, link lists, empty state, expanded-first/collapsed-after ordering, and stable identity. Entity assemblers supply explicit ground-type metadata, ground/basis metadata, and neighbors; a neighbor is deduplicated within a ground but may correctly appear under multiple grounds. A presentation group may optionally supply read-only rich expanded content through the shared callback slot, which receives the existing `onNavigate`; without it, the renderer uses the unchanged shared neighbor-link list. The slot cannot own disclosure, focus/filter state, card identity, or layout. A neutral shared semantic presenter consumes only an adapted read-only view model: navigable basis and neighbor entities, optional explanation and contributor groups, and optional ordered Job → Desired Outcome comparison categories whose leaves may carry contributor-provenance rows. Offer and Touchpoint adapters remain projection-specific; projection/domain records never enter `NeighborhoodGroups`. Both Inspectors use the same compact collapsed cards, semantic-content selectors, wrapping, focus treatment, geometry, filters, and packed layout.

The shared focus controls form one lightweight panel rather than separate internal containers. Ground types are its primary content and use shared horizontal checkbox chips: each visible native checkbox and its wrapping label text form one wholly clickable label. Inspector-wide form rules must not stretch the checkbox or turn its label into a grid: the native checkbox stays on the left and the label text stays to its right, wrapping within the remaining chip width when necessary. Chips wrap with the available width, and hover, checked, and visible chip-level keyboard-focus states supplement rather than replace the recognizable native checkbox. A nearby secondary cluster contains Dim/Hide as one compact segmented control with recognizable native radios and Reset as a lower-weight separate action. The primary and secondary content wrap responsively inside the single panel without introducing nested panel framing.

Nested semantic-neighbor regions use natural content height and their local spacing. Generic page-section margins, side/bottom padding, frame background, and border do not apply to these regions; only the intended local top padding and dashed separator remain. Packed Neighborhood layout measures those corrected natural card heights and recalculates placement rather than compensating for nested-section box-model inflation.

The Neighborhood root has no outer perimeter frame, background or underlay, radius, or shadow. Its dashed top separator is the shared major-section boundary for both Offer and Touchpoint, with the heading and `Derived` badge placed below it by shared top padding; the separator is not a fieldset border and does not cross the heading. Touchpoint Neighborhood is a sibling immediately after Business structure rather than a descendant of the `.touchpoint-business-structure` frame. Individual Neighborhood cards retain their own containers. Ground types, Focus mode, and Reset instead share the single lightweight controls panel described above; the internal fieldsets add no independent border or background.

- The compact overview contains one native checkbox for each type represented by the supplied nonempty grounds, deduplicated by `groundTypeId` in first-appearance order. Its named type and mode groups, labels, and Reset action wrap at narrow widths without clipping meaningful text or causing horizontal overflow. Controls retain a visible `:focus-visible` indication.
- With selected types, Dim preserves the complete ordered card set and packed panel-ID input while applying only a semantically neutral visual de-emphasis to nonmatching cards. Dimmed cards and their disclosure/entity links remain keyboard-operable and are not disabled, hidden from accessibility APIs, inert, or removed from tab order. An empty selection removes all de-emphasis regardless of mode.
- Hide renders and measures the same filtered ordered set of matching cards, passing only their IDs to the existing packed-layout owner so measurements and container height reflow without stale panels. Returning to Dim or resetting restores the full ordered set and its unchanged geometry/disclosure state. No alternate layout algorithm or entity-specific width/modifier is introduced.
- `initialCompactOverviewExpandedGroupIds()` supplies initial compact disclosure density: one group of at most four opens; two groups open when each is at most four and their total is at most six; otherwise groups start collapsed. This current common overview rule does not establish domain semantics.
- `usePackedPanelLayout` is the generalized measured-layout owner. Neighborhood uses current 14–20rem tracks and `.65rem` gap; the CSS Grid fallback is `repeat(auto-fit, minmax(min(100%, 14rem), 20rem))`, left aligned, and becomes one column under the current `30rem` media query. Adaptive use of available width and narrow fallback are contract; constants remain shared implementation values.
- Expanded groups precede collapsed groups visually and in the renderer's ordered list. Stable group IDs preserve disclosure state. Variable measured heights feed shortest-column placement; CSS Grid remains readable when `ResizeObserver` is unavailable.
- Rich content remains inside the existing disclosure content. Offer semantic cards use ordinary Inspector entity links for their concrete basis and neighboring Offers. DO-bearing Job cards may reuse the mini-dendrite vocabulary for Job → Desired Outcome comparison categories, while preserving the shared 14–20rem geometry, wrapping, packed-layout input, and focus grammar. This presentation capability does not make Offer ontology a shared renderer concern.
- The hook owns measured container height and absolute transforms. A future user reuses it rather than adding a packing algorithm. Browser checks must measure columns, variable heights, overlap, horizontal overflow and resize recalculation; pure `calculatePackedPanelLayout` tests cannot prove rendered geometry.

### Neighborhood transfer checklist

This checklist is mandatory during Plan for a new Inspector kind or an extension of Neighborhood, together with the [functional contract](./inspector-neighborhood-functional-contract.md) and [interaction contract](./inspector-interaction-contract.md). The accepted Offer/Touchpoint presentation is the reference; old screenshots or prompts do not authorize redesigning it.

1. **Define the ontology-owned projection first.** List the inspected kind, valid same-kind neighbors, each concrete basis and type, committed records/path validity, stable IDs, counts, ordering, deduplication, and any unresolved semantics. Ground types are metadata, not new domain entities. Do not copy Offer or Touchpoint grounds or assume the six Client-intent kinds apply to another entity kind.
2. **Identify owners before JSX.** Put entity-specific matching in a pure derived helper and map its result to `NeighborhoodPresentationGroup` in the Inspector assembly. Use `SemanticNeighborhoodContent` only when its read-only view model fits; pass ordinary navigation through `onNavigate`. Keep the shared `NeighborhoodGroups` owner of chips, mode/Reset, disclosure, cards, packing, and transient state. A genuine missing shared capability requires an explicit plan, not a parallel renderer.
3. **Reuse the accepted visual and interaction contract unchanged.** A single lightweight Ground types + Dim/Hide + Reset panel; native horizontal checkbox chips; a dashed major-section separator without an outer Neighborhood frame; naturally sized nested semantic sections; shared packed widths/reflow; keyboard-focus visibility; reset-on-owner-change and independent disclosure. Keep registry references distinct from navigable graph entities.
4. **Guard both the new kind and existing references.** Test valid and empty grounds, counts/duplicate neighbors, actual local selection versus upstream availability where relevant, mixed structural/semantic types, OR/Dim/Hide/Reset, stable disclosure, navigation and document immutability. Re-run affected Offer and Touchpoint tests when changing shared presentation/interaction or matching helpers.
5. **Verify geometry at the actual owner.** Check computed CSS cascade, native input/label alignment, long-label wrapping, natural-height nested regions, ResizeObserver-driven packing, overlap/overflow, and width changes in a real browser where available. DOM and pure layout tests alone do not prove rendered geometry. Record exact checks performed and all unavailable browser/assistive-technology checks separately.
6. **Update the source of truth together.** When changing accepted semantics, behavior or a shared visual rule, update its owning contract, implementation owner and affected regressions in the same PR. Leave deferred Repulsor grounds, Product/Client-side semantics and Map dim/hide outside a new Inspector task until separately approved. Product/Offer legacy section-wide Apply is not a reusable Inspector editing contract.

## Client Scope read state

The Touchpoint read projection comes from `touchpointClientScope()`. It renders nonempty panels for the six canonical kinds: Core Functional Job, Related Job, Consumption Chain Job, Emotional Job, Social Job, and Financial Desired Outcome.

- Panels use count badges and independent progressive disclosure. DO-bearing Jobs show Job → Desired Outcome mini-dendrites; Emotional/Social Jobs do not acquire fake ordinary outcomes; Financial Desired Outcome is an independent leaf. Titles are semantic entity navigation links.
- The same `initialCompactOverviewExpandedGroupIds()` density and expanded-first presentation apply. `ClientScopePackedGroups` calls `useClientScopePackedLayout` with current 18–22rem panels and `.65rem` gap. `.client-scope-view-groups` provides the readable auto-fit Grid fallback.
- Stable panel IDs, logical DOM/focus order, measured visual placement, explicit container height, and resize recalculation are contractual. Packed visual coordinates must not be mistaken for ontology or persisted order.
- Resistance remains outside the Client Scope panel grid because it is a different derived/authored semantic surface, not a seventh Client kind.

## Client Scope edit state and Resistance

- The edit state stays within the persistent Client Scope section. `Search Client intent`, compact kind shortcuts, and upstream-source disclosures expose global discovery and provenance. Candidate presentation must distinguish checked, incomplete, invalid and contributor-resolver states.
- `globalIntentDiscovery()` and `touchpointUpstreamSources()` own the projection; contributor choices and eligibility are not presentation inventions. A DO-bearing path remains visibly incomplete until its outcome/contributor context is resolved.
- `touchpointResistanceSection` presents relevant Repulsors with a `Derived` marker, navigable Repulsor title, and authored `Mitigated here` checkbox. Derived relevance must not resemble or silently become authored mitigation.

## Cross-cutting presentation

- Follow existing type hierarchy (document title, section heading, structural heading, property heading, metadata/status), spacing rhythm, border/color vocabulary, and shared control classes. Accent-underlined entity links communicate navigation; buttons communicate authoring/dismissal; muted chips/text communicate metadata, not actions.
- Consequential values currently include the document maximum, Business grid/collapse, compact panel min/max/gaps, narrow Neighborhood fallback, `min-width: 0`, wrapping, and measured container height. Change them only at their shared owners with regressions. Border radii, padding, font sizes, and indicator dimensions are current implementation unless evidence shows layout/accessibility significance.
- Long text wraps; flex/grid children keep `min-width: 0`; external URLs and link lists must not cause horizontal overflow. Visible `:focus-visible` styling is required wherever the current shared classes provide keyboard interaction.
- There is no accepted viewport matrix. CSS breakpoints currently in `styles.css` describe implementation, not promised device support. Test available container width, not viewport alone.
- Ontology can justify different fields, relations, eligibility, copy and derived grounds. It does not justify parallel widths, cards, disclosure models or action styling.

## Reuse boundary

**Reuse:** document frame; semantic visual language; heading edit affordance; entity-link treatment; local embedded editors; independent property commits; recoverable validation; local action grouping; transient disclosure/scroll restoration; owner-aware focus; semantic-completeness commit presentation; dismissal/focus grammar; disclosure state model; adaptive/packed panels; navigation/history; validation and confirmation boundaries.

**Do not copy literally:** Offer Content fields, URL meaning, empty-state copy, first-nonempty-paragraph preview rule, or canonical Offer duplication contents; Product → Offer → Touchpoint structure; Offers, Located in, Parent or Children; Touchpoint containment/reassignment; six Client Scope kinds as mandatory sections; contributor propagation; Resistance relevance/mitigation; specific labels, counts or empty copy; Touchpoint candidate eligibility or domain operations.

A future Inspector first identifies its ontology-owned properties and relations, then applies the common presentation and interaction contracts.

## Maintenance and evidence rule

An accepted common-pattern change must update in one change: (1) this or the interaction contract, (2) the shared implementation owner, (3) regressions for the Touchpoint reference, and (4) regressions for every other affected Inspector kind. An entity-specific exception requires an ontology rationale. A small present card count never justifies a separate width or disclosure contract.
